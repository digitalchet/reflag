# Project structure

```text
Reflag/
├── .github/          GitHub community and security files
├── assets/flags/     Runtime flag SVGs
├── design/           Editable visual source files
├── docs/             Project and policy documentation
├── icons/            Runtime browser icons
├── media/screenshots Store and promotional preview images
├── releases/         Local release builds, ignored by Git
├── tests/            Development regression checks
├── website/          Future product website
├── manifest.json     Manifest V3 entry point
├── content.*         Page renderer
├── popup.*           Toolbar interface
├── options.*         Full settings interface
├── regions.js        Continental flag registry
├── README.md         Project overview and installation
└── LICENSE*          Code and artwork licences
```

## Why the extension remains at the root

Chrome, Edge, Opera, and other Chromium browsers expect `manifest.json` at the root of the folder selected with **Load unpacked**. Keeping the manifest and its runtime files here makes a repository clone immediately loadable and avoids maintaining a duplicate source tree.

## Releases

Place unpacked release folders and ZIP archives in `releases/`. Their contents are excluded from version control because Git already records the source used to produce each release. Published binaries can instead be attached to versioned GitHub Releases.

## Design and runtime artwork

Editable source artwork belongs in `design/`. Exported icons required by the browser belong in `icons/`, while bundled flag artwork belongs in `assets/flags/`. This distinction keeps working files separate without breaking paths declared in the manifest or generated by the renderer.

## Website and promotional media

The future product website belongs in `website/` and should remain independently buildable and deployable. Store screenshots, social previews, and other promotional imagery belong in `media/screenshots/`; their editable source files can remain in `design/`.
